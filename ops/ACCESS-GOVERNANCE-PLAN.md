## ١. الخلاصة التنفيذية

### المشكلة

الشاشة الحالية (`admin/Roles.tsx`، ٥٦ سطراً) تعرض **مصفوفة ٦×٦ مكتوبة يدوياً** لا يقابل أيَّ خانةٍ فيها ديكوريتور `@Roles` حقيقي. هي ليست ناقصة فحسب — **هي مضلِّلة**:

| ما تعرضه | الحقيقة في الخادم |
|---|---|
| ٦ صلاحيات | **٤٣ نقطة نهاية** (٣٦ محروسة بـ`@Roles` + ٣ قراءات مفتوحة + ٤ جلسة/بنية) |
| `signContracts` | **لا وجود لها** — لا نقطة نهاية للتوقيع في المنظومة |
| علامة ✓/— ثنائية | ثلاث حالات فعلية: نافذة / نافذة **ضمن نطاق الشركة** / ممنوعة — لأن `scope.ts` يقيّد أدوار المقاول فقط |
| صفر مستخدم | `UsersModule` كامل: `GET/POST/PATCH /api/users` |
| صفر إجراء | ٥ إجراءات مدعومة خادمياً + ٤ حرّاس صارمين غير مرئيين |

### الأطروحة

نستبدلها بالنمط الذي أثبت نفسه في هذا التطبيق نفسه — **سجل ← ملف ٣٦٠° ← مرجع** — نظير `Vendors.tsx → EntityProfile.tsx` حرفياً.

**القانون الحاكم للقسم، وهو معيار القبول لكل عنصر فيه:**

> **لا يُعرض هنا ما لا تفرضه نقطة نهاية، ولا يُسجَّل ما لا يقع، ولا يُنسب فعل إلى اسم قابل للتغيير.**

والحلقة مغلقة بثلاث قفزات: صفُّ السجل يفتح الملف ← صلاحيةُ الملف تفتح المرجع مصفّى عليها ← خليةُ المرجع تعيد إلى السجل مصفّى على حامليها.

## ٣. الشاشات الثلاث

### شاشة أ — سجل المستخدمين والوصول · `#/admin/users`
**ملف:** `admin/Users.tsx` (نظير `Vendors.tsx`)
**الغرض:** «من يملك وصولاً، بأي دور، بأي نطاق، وأين يُرفض» — سطح واحد قابل للتصنيف والبحث.

| المنطقة | المحتوى |
|---|---|
| ١ الترويسة | `op-page__head` — العنوان + عدّاد + `op-btn-primary` «أضف حسابًا» + `op-btn-ghost` «تصدير CSV» |
| ٢ الإفصاح | `wz-note--info` وضع العرض المحلي · و`wz-note--warn` مشروط: «إدارة الحسابات محصورة بمشرف رئيسي — جلستك {{role}}» |
| ٣ مؤشرات | `ad-kpis` × ٤: حسابات مفعّلة · **مشرفون رئيسيون مفعّلون** (أحمر عند ١) · **أدوار حوكمية بلا حامل** · حسابات معطّلة |
| ٤ الترشيح | `op-search` بالاسم/البريد + شرائح `wz-chip` بعدّادات + `acc-scope-select` للنطاق |
| ٥ الجدول | `op-tbl` بسبعة أعمدة |

**الأعمدة السبعة:** الحساب (صورة رمزية + اسم + بريد) · الدور (`acc-role` + الرمز الخام) · النطاق (شركة أو «نطاق المنظومة») · الصلاحيات النافذة (`n` إجراء · `m` قراءة) · المصادقة الثنائية · الحالة · آخر إجراء موثّق.

> **مؤشّر ٣ يستبدل** بطاقة «بلا مصادقة ثنائية». سبب الاستبعاد: مسار الدخول الحالي **لا يفرض** 2FA، فلا يجوز عرضها كضمانة. أما «دور حوكمي بلا حامل مفعّل» فنتيجة خادمية حقيقية: كل استدعاء يُرفض ٤٠٣ ويُسجَّل `ROLE_REFUSED`.

### شاشة ب — ملف الوصول ٣٦٠° · `#/admin/users/:id`
**ملف:** `admin/UserProfile.tsx` (نظير `EntityProfile.tsx` عنصراً بعنصر)
**الغرض:** «ماذا يستطيع هذا الشخص بالضبط، ماذا **لا** يستطيع، ومن غيّر له ذلك ومتى».

- **الترويسة** `file-head`: الاسم + `acc-role` + `acc-status` + وسوم مشروطة «حسابك» / «آخر مشرف رئيسي مفعّل»، ثم البريد و`azureOid` والنطاق.
- **`acc-actionstack`** — أزرار الحوكمة، وتحت كل زرٍّ معطَّل **سطر `wz-gate` يحمل سبب المنع الحرفي** (البوابة قبل الزر، لا رسالة خطأ بعده).
- **العمود العريض** «الصلاحيات النافذة» — مجمّعة بالمجال، وفيها عمود **النطاق يُحسب لكل صف×دور**: `cap.scoped && isOperatorRole(u.role)` ← «ضمن شركته»، وإلا «كل المنظومة».
- **العمود الضيّق**:
  - **«ما لا يستطيعه هذا الحساب»** — لوحة فصل المهام: أهم ٦ صلاحيات محجوبة + **من يملكها** («يملكها: إدارة ROC · مشرف رئيسي»). هذا ما يجعل فصل المهام قابلاً للتدقيق: الفراغ مُعدَّد ومنسوب.
  - **«سجل حوكمة الحساب»** — الأثر الإلحاقي، وفيه **الفاعل والنتيجة**: `by.name (الدور)` ووسم أحمر «مرفوض» على المحاولات المرفوضة.

### شاشة ج — مرجع الأدوار والصلاحيات · `#/admin/roles`
**ملف:** `admin/RolesMatrix.tsx` (يحلّ محل `Roles.tsx` كلياً)

**خمس حالات للخلية** — وهي الرسم الأمين الوحيد:

| الرمز | المعنى | المصدر |
|---|---|---|
| ✓ | نافذة | الدور في `@Roles` |
| ✓⌐ | نافذة **ضمن نطاق شركته** | `scoped && isOperatorRole` |
| ○ | بلا `@Roles` | `roles.guard.ts` يعيد `true` عند غياب البيانات الوصفية |
| — | ممنوعة | الدور خارج القائمة |
| ⊘ | خارج الجلسة | نقاط الدخول/الصحة — مستبعدة من كل عدّاد |

- **شريط المصدر:** «مستمدّة من `@Roles` في `apps/api/src/**/*.controller.ts` — نسخة {{rev}} · آخر استخراج {{date}}». وعند تجاوز ٣٠ يوماً يتحوّل إلى تحذير.
- **العمود الأخير «الحاملون»:** عدد الحسابات المفعّلة الحاملة للصلاحية → يقفز إلى السجل مصفّى. و**الصفر يُرسم أحمر** لأن صلاحية حوكمية بلا حامل عيبٌ تشغيلي لا مجموعة خالية.
- **تبويب «حسب الدور»:** ست بطاقات + **مقارنة دورين**: الفرق `OPERATOR_ADMIN − OPERATOR_USER` = `{cancelTender, suspendTender, resumeTender}` بالضبط (متحقَّق).

## ٤. نموذج بيانات الصلاحيات

**ملف:** `admin/capabilities.ts` — هو **مصدر السلطة المعروض على الشاشة**.

```ts
export type ApiRole = 'SUPER_ADMIN'|'ROC_ADMIN'|'EVALUATION'|'AUDITOR'|'OPERATOR_ADMIN'|'OPERATOR_USER';
export type CapDomain = 'tenders'|'mct'|'contracts'|'vendors'|'users'|'audit'|'holidays';
export type Guard = 'roles'|'open'|'session';

export interface Capability {
  id: string; domain: CapDomain;
  method: 'GET'|'POST'|'PATCH'|'DELETE'; route: string;
  roles: ApiRole[];          // قائمة @Roles الحرفية؛ [] للمفتوحة والجلسة
  scoped: boolean;           // operatorScopeWhere / loadScopedActive
  stateGated: boolean;       // loadScopedActive يرفض الملغاة/الموقوفة (٤٠٠)
  clause: string;
  guard: Guard;
  label: { ar: string; en: string };   // نسق {ar,en} كما في Tender.title
  mutating: boolean;
}
export const CAP_REV = 'gt-2026-07-22';
export const CAPABILITIES: Capability[] = [ /* ٤٣ صفاً منقولة ١:١ */ ];
```

**المطابقة العددية — لا تنحرف:**
- ٤٣ = **٣٦ محروسة + ٣ قراءات مفتوحة + ٤ جلسة/بنية**
- الكون المعدود = **٣٩** (٣٦ + ٣). الأربع الأخيرة لا تدخل أي عدّاد — ولهذا يقرأ المدقّق **صفر إجراء مؤثّر** بصدق.
- `SUPER_ADMIN` ∈ **٣٦/٣٦** المحروسة → ختم «يجمع الواجبات» واقعة مستخرَجة لا رأي.
- توزيع المجالات: المناقصات ١٧ · لجنة الكلف ٤ · العقود · المجهزون · المستخدمون · التدقيق · العطل.

**حارس الانحراف:** `apps/web/test/capabilities.test.ts` — **لاحظ المسار**: `vitest.config.ts` يلتقط `apps/*/test/**` فقط، فوضعه تحت `src/` يعني ألّا يُنفَّذ أبداً.

```ts
expect(CAPABILITIES).toHaveLength(43);
expect(CAPABILITIES.filter(c => c.guard === 'roles')).toHaveLength(36);
expect(CAPABILITIES.filter(c => c.guard === 'roles' && !c.roles.includes('SUPER_ADMIN'))).toHaveLength(0);
```

> **صياغة أمينة على الشاشة:** «يتحقّق `capabilities.test.ts` عند `npm run test`» — **وليس** «عند كل بناء»: `build` هو `vite build` مجرّداً من فحص الأنواع والاختبار.

## ٥. الإجراءات الخمسة

كلٌّ منها: مُطلِق ← بوابة تعكس حارساً خادمياً ← نافذة ← تأكيد ← صف تدقيق ← إشعار.

| # | الإجراء | البوابة (تعكس الخادم حرفياً) |
|---|---|---|
| أ | **أضف حسابًا** | `azureOid` حقل أول الدرجة مع مصدره من Entra + فحص تكرار البريد/المعرّف · أدوار المقاول تُلزم بشركة |
| ب | **غيّر الدور** | الذات → «لا يمكنك خفض دورك بنفسك» · آخر مشرف رئيسي → «عيّن مشرفًا آخر وفعّله أولًا» · **تحذير قبل الإقرار عند تصفير آخر حامل لدور حوكمي** |
| ج | **انقل النطاق** | يظهر لأدوار المقاول فقط · لا شركات مسجّلة → معطّل |
| د | **بدّل المصادقة الثنائية** | إفصاح: «سمة مخزَّنة يقبلها الخادم؛ مسار الدخول لا يفرضها» |
| هـ | **عطّل / أعد التفعيل** | لا حذف أبداً — التعطيل نهائي (`users.controller.ts:7`) · الذات وآخر مشرف رئيسي ممنوعان |

**آلية التدقيق المصحّحة:** الحيلة العامة في `applyAndAudit` تنتج صفاً **متطابقاً** للمنفَّذ والمرفوض. لذا تنضم إجراءات الوصول إلى `NON_AUDITED`، و**`apply()` يكتب صفّه الدقيق بنفسه** حاملاً `outcome:'applied'|'refused'` و`reasonCode`.

**مطابق التدقيق المتين:** صفوف العميل تكتب `target = email`، وصفوف الخادم المُحمَّلة قد تكتب `${email}: OLD→NEW`:
```ts
const matchUser = (email: string) => (a: AuditEntry) =>
  a.target === email || a.target.startsWith(email + ':');
```

> **حدّ الصدق:** `AuditEntry` الخادمي بلا فاعل، و`ROLE_REFUSED` يفهرس على المسار لا على الشخص. لذا وعد «منسوب لفاعل» **يقتصر على الأحداث المكتوبة من العميل** — ولا يُوحى بغير ذلك.

## ٦. تغييرات المتجر والجلسة

```ts
// State — store.tsx:181
users: UserAccount[];        // مضاف
operators: OperatorOrg[];    // مضاف — مصدر operatorId الذي يطلبه الخادم

// UserAccount — ١:١ مع model User، بلا createdOn (النموذج لا يملكها)
{ id, azureOid, name, email, role: ApiRole, operatorId?, twoFa, disabled, events? }

// UserEvent — يمدّ VendorEvent بما ينقصه للتدقيق
{ kind: 'create'|'role'|'scope'|'twofa'|'disable'|'enable'|'refused',
  reason, on, at, by: { oid, name, role }, detail? }

// AuditEntry — إضافات اختيارية متوافقة رجعياً
by?: { oid, name, role };  outcome?: 'applied'|'refused';  reasonCode?: string;

// OperatorOrg — nameEn اختياري (schema.prisma:23 قابل للإفراغ)،
// وfinancialAuthorityUSD يصل نصاً من Decimal(18,2) → يلزم تحويل
{ id, name, nameEn?, financialAuthorityUSD: number }
```

**حرّاس مشتركة بين الواجهة والمُخفِّض** (مصدر واحد للحقيقة): `enabledSuperAdmins`, `isLastEnabledSuper`, `scopeConsistent`.

### الجلسة — الفخّ المزدوج

```ts
export type Role = 'operator-admin' | 'roc-admin' | 'super-admin';   // + super-admin
export interface Session { name; role: Role; company?; oid: string } // + oid
```

الارتباط بالهوية في كل مكان: `state.users.find(u => u.azureOid === session.oid)` — **ثابت وفريد، لا بالاسم القابل للتغيير**.

> ⚠️ **مزلقان لا بدّ منهما:**
> 1. `session.ts:19` هو `JSON.parse(raw) as Session` بلا فحص. جعل `oid` إلزامياً يعني أن أي جلسة قائمة تُفكَّك بـ`oid === undefined` فتختفي كل الإجراءات لمشرف رئيسي شرعي. **الحل:** ترقيم مفتاح الجلسة أيضاً (`masaar-session-v2`).
> 2. توسيع `Role` يمرّ صامتاً عبر **ثلاثة** مواضع تُثلِّث على دورين فقط: `store.tsx:918`، `store.tsx:939`، `OperatorShell.tsx:266`. لا يكسر فحص الأنواع — فيشحن الخطأ صامتاً. تُعالَج جميعاً.

### الاستمرارية — نُهاجر ولا نُتلف (8.1-e)

`KEY` → `masaar-operator-v5`، لكن **مع ترحيل يحفظ سجل التدقيق الإلحاقي** بدل إهداره. حارس الشكل الحالي (`store.tsx:889`) يفحص `tenders/audit/vendors` فقط، فسيقبل كتلة v4 في شكل v5 مُنتِجاً `users: undefined` — وهو ما ينهار عليه `AdminShell` في **كل** مسار إداري.

## ٧. الأنماط والترجمة

- **CSS:** كتلة `acc-*` جديدة في `admin/admin.css` — من الرموز حصراً، وبخصائص منطقية فقط، مع `direction:ltr; unicode-bidi:isolate` على كل حقل أحادي المسافة (البريد، المعرّف، `ROC_ADMIN→EVALUATION`).

- **الأيقونات:** الجهات → `building`، والأدوار → **`lock`** (لأن `shield` محجوزة للامتثال).
- **i18n:** `access.*` و`caps.*` كاملتين بالعربية والإنجليزية؛ وتُحذف `roles.perm.*` و`roles.scopeNote` و`roles.hint` لأنها تصف صلاحيات غير موجودة. **تسميات الصلاحيات تعيش في `capabilities.ts` كـ`{ar,en}`** لأنها بيانات لا نصوص واجهة.

| البند | السبب |
|---|---|
| ترتيب الأعمدة + ترقيم الصفحات + عدّاد النتائج | السجل يرسم كل الصفوف بلا حدّ |

| `aria-describedby` بدل `title` وحده | كل سند السلطة يعيش في تلميحات غير مقروءة للقارئات |
| تحديد متعدّد + تعطيل جماعي + **شهادة مراجعة وصول دورية** | المراجعة الدورية مستحيلة صفّاً صفّاً |

| مسار تصحيح الاسم/البريد | معرّف Entra خاطئ ينتج حساباً ميتاً غير قابل للحذف |

**غير مدعوم صراحةً — ويُصرَّح به على الشاشة:** *التفويض المؤقّت أثناء الإجازات* — لا نقطة نهاية له. البديل المشروع: حساب مستقلّ مقيّد النطاق. تُذكر بوضوح كي لا يُفهَم التعطيل بديلاً عن التفويض.

## ملحق أ — مفارقة تسمية مقصودة عن وثيقة المواصفات

**القرار (المستخدم، 2026-07-22): يُعتمد «المشغّل».**

وثيقة المواصفات `_handoff_masaar_website/spec.html` §3 تسمّي الدورين حرفياً **«مدير حساب مقاول»** و**«مستخدم مقاول»**، والكيان فيها هو **المقاول الرئيسي (Lead Contractor / IOC)** — ١٢ شركة، عقد الخدمة لكلٍّ منها هو مصدر الصلاحية المالية (§٧). والمورّد في السجل هو **المقاول الثانوي**.

فالتسمية الأصلية **لم تكن خطأً** بل اختصاراً أميناً للوثيقة. سبب العدول عنها:
1. «مقاول» مجرّدةً تلتبس بالمقاول الثانوي في واجهة تعرض الاثنين معاً؛
2. الوثيقة نفسها تستعمل «**الشركات المشغّلة**» للكيان ذاته (§1)؛
3. التطبيق يقول «بوابة المشغّل» منذ نشأته.

**التبعة:** أي مقابلة لاحقة مع الوثيقة يجب أن تعلم أن «مقاول رئيسي» فيها = «مشغّل» هنا. ولو أُريد العودة للوثيقة حرفياً فالبديل هو «مدير حساب المقاول الرئيسي» (مع «الرئيسي» صراحةً، لا «مقاول» مجرّدة).

## ملحق ب — تعارض مُوثَّق بين الوثيقة والتنفيذ

| الصلاحية | الوثيقة (§3) | الخادم | المعالجة |
|---|---|---|---|
| **دعوة/إنشاء المستخدمين** | تمنحها لـ«مدير حساب المشغّل» | `users.controller.ts` بـ`@Roles('SUPER_ADMIN')` على مستوى الصنف | **لم يُحسم** — يُعرض في المرجع بحالة سادسة `⚠` ولوحة تفسيرية |

النموذج: `Capability.specGrants?: ApiRole[]` — الأدوار التي تمنحها الوثيقة ويرفضها الحارس. و`cellState` يُعيد `'conflict'`، و`roleHas` **لا يعدّه امتلاكاً** (الحارس هو المرجع في كل عدّ ومؤشّر). مثبَّت باختبار: `specConflicts()` = `['createUser']` بالضبط.

**المبدأ:** التعارض بين وثيقة حاكمة وكودٍ يفرض غيرها ليس تفصيلاً تُخفيه الواجهة — يُعرض ليَحسمه صاحب الصلاحية.

## ملحق ج — بنود من الوثيقة لم تُنفَّذ بعد

- **`IP` في سجل التدقيق**: الوثيقة §10 توجب «(مستخدم، فعل، هدف، وقت، **IP**)» — الحقول الأربعة الأولى موجودة، والخامس يتطلّب الخادم.
- **سند فصل المهام ٥.١**: «لا يجوز لأي فرد استخدام أي حيلة لتجاوز آليات الرقابة أو تضارب المصالح (5.1)» — سندٌ مرقّم يصلح لترويسة لوحة «ما لا يستطيعه هذا الحساب»، وهي بلا سند اليوم.
- **ملف المشغّل ٣٦٠°**: الوثيقة §10 تنصّ على شاشة «تفاصيل المقاول الرئيسي — حساباته، مناقصاته، **التزامه بالمدد**». بُني السجل دون الملف.
- **إدارة PCD** (دائرة العقود والمشتريات لكل مشغّل): غير مُنمذجة إطلاقاً.

## ملحق د — مسألة مفتوحة تتجاوز هذا القسم

`App.tsx:250` يفحص **وجود** الجلسة لا **دورها**، فأي حساب مقاول يفتح لوحة الإدارة كاملة. هذا لا يُصلحه هذا القسم وحده — لكنه يفقد قسم حوكمة الوصول معناه إن بقي. يُقترح بندٌ منفصل: بوّابة دور على مستوى المسار.
