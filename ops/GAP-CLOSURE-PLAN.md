## المسار ٠ — توحيد الأرقام لاتينيةً (معزول · يُنفَّذ أولاً)

**لماذا أولاً:** لا يعتمد على شيء، ولا يعتمد عليه شيء، ويلمس كل شاشة — فإنجازه مبكّراً يمنع تكرار الخطأ في المسارات التالية.

**تصحيح المستشار العدائي (مؤكَّد):** النطاق الأصلي كان يفشل في معياره — لأنه يغفل مصدرين حقيقيين للأرقام العربية-الهندية وقت التشغيل، ومثاله المرجعي كان مُختلَقاً.

### 0.1 مُنسّق الأعداد يصير لاتينياً دائماً
- `apps/web/src/operator/derive.ts:154` — `fmtCount` يستعمل `ar-EG` (أرقام عربية-هندية). التغيير: `en-US` دائماً بصرف النظر عن اللغة. تُبقى وسيطة `lang` للاستقرار (٢٣ مستدعياً) لكن تُهمَل مع تعليق.
- `fmtMoney` (`derive.ts:159`) **صحيح أصلاً** (`$2,000,000` عبر `en-US`) — يبقى بلا تغيير. قرار العميل: إبقاء `$`.

### 0.2 التواريخ المحلّاة وقت التشغيل (أمسكها المستشار — كانت غائبة)
- `Inbox.tsx:26` وأي `toLocaleDateString('ar', …)`/`toLocaleString('ar', …)`: لوكيل `ar` يطبع أرقاماً عربية-هندية افتراضياً. التغيير: استعمال `ar-u-nu-latn` (نظام الأرقام اللاتيني صراحةً) في كل تنسيق تاريخ محلّى — يبقى اسم الشهر عربياً والرقم لاتينياً.
- مسح شامل لكل `toLocale*('ar'…)` في `apps/web/src` قبل الاعتماد.

### 0.3 كنس الأرقام العربية-الهندية من نصوص الترجمة
- `apps/web/src/locales/ar.json` — استبدال محارف U+0660–0669 (٠-٩) بـ ASCII في **قيم** المفاتيح. **تصحيح:** «١٢.٤.٢» ليست في الملف أصلاً (كل مرجع 12.4.2 لاتيني سلفاً)؛ الأرقام الفعلية هي «(٦.٩)» و«(١٢.٢.٢)» و«(١٢.٢)» و«§٧» — تصير «(6.9)»… إلخ.
- تنبيه bidi: تسميات النماذج «م/١»/«ح/١» (`ar.json:524,583`) تصير «م/1»/«ح/1» — قرار العميل «بلا استثناء» يشملها، مع التحقّق البصري من اتجاه المحرف.
- **التحقّق أن الكنس لا يفسد المطابقة:** الكود لا يطابق على قيم الترجمة إطلاقاً؛ معرّفات البنود في الكود سلاسل ASCII مكتوبة (`capabilities.ts` وحقول `clause`). آمن.

### 0.4 حارس انحدار موسّع (أوسع من ar.json)
- اختبار `latin-digits.test.ts` (٥ فحوص): (أ) خلوّ **الترجمتين** من U+0660–0669/06F0–06F9، (ب) **مسح المصدر كلّه** `*.ts/*.tsx` (القناة التي يغفلها فحص الترجمة — نصّ JSX مثل «٣ صحف» يمرّ بلا هذا)، (ج) `fmtCount`/`fmtMoney` لاتيني، (د) `fmtDate` يثبت تحميل بيانات ar العربية (`/يوليو/`) مع أرقام لاتينية.
- `fmtDate` في `derive.ts` — الباب المحكوم الوحيد للتواريخ: `ar-u-nu-latn` + تطبيع حتميّ بـ`toLatinDigits` (يصمد تحت أي ICU). كل استدعاء تاريخ محلّى يمرّ به لا بـ`toLocaleDateString` خام.

### 0.5 استثناء موثَّق: حقول `input type="date"` الأصلية (أمسكه المستشار)
- خمسة حقول `type="date"` (ContractProfile · EntityProfile · AdvertiseWizard · CompleteWizard ×2) — **عنصر متصفّح**: يعرض قيمته بلوكيل واجهة المتصفح لا بلغة الصفحة، فقد يُظهر لمستخدم على متصفّح عربي أرقاماً عربية-هندية. **القيمة المخزَّنة ISO لاتينية دائماً** — الأثر بصريّ عابر في الودجت لا في البيانات، وفحص `innerText` أعمى عنه بنيوياً.
- **قرار مطلوب من العميل:** إمّا قبوله استثناءً موثّقاً (قشرة متصفّح خارج تحكّم التطبيق)، أو تفويض استبدالها بحقل تاريخ مخصّص (نصّي بنمط + تحقّق) — عمل مستقلّ. حتى يُحسم: موثَّق بتعليق عند كل حقل.
- **معيار القبول:** لا رقم عربي-هندي واحد في واجهة التطبيق — متحقَّق بالمتصفح **على صندوق اليوم تحديداً** + المصدر + الترجمتان · `$2,000,000` باقٍ · الاستثناء الوحيد (حقول التاريخ الأصلية) موثَّق لا مخفيّ.

## المسار ١ — عقد الخدمة + الحقول (المكدّس الكامل · يفكّ العقدة الجذرية)

**العقدة:** `FINANCIAL_AUTHORITY_USD = 5_000_000` ثابتٌ مثبَّت، والمخطط نفسه يقول «from the Service Contract (§7) — never hardcoded». عقد الخدمة هو مصدر الصلاحية المالية نصّاً (spec C0.3) و**النص الذي يعلو على الدليل عند التعارض (SCPP 4.c)**. حتى تُنمذَج، تبقى كل حسابات MCT/ROC مبنية على رقم وهمي.

**نُقّح بالكامل بعد هجوم المستشار (حكم: غيّر-أولاً — خمسة عيوب في المخطط + رابع/خامس رِبل).**

### 1.1 Prisma — المخطط المصحَّح
```
model Field {                       // الحقول النفطية — 13 حقلاً (spec §1)
  id, name, nameEn?, code @unique,
  operatorId → Operator,
  serviceContract ServiceContract?  // 1:1 — قرار واعٍ: التجديد PATCH مُدقَّق، لا صفّ ثانٍ
  tenders Tender[]
}
model ServiceContract {             // مصدر الصلاحية المالية (§7)
  id, code @unique,
  fieldId @unique → Field,          // المشغّل يُشتقّ عبر الحقل — لا operatorId مخزَّن (عيب ١: يسمح بالانحراف)
  financialAuthorityUSD Decimal,
  signedOn, expiresOn,              // عيب ٢: نُخزّن اثنين فقط؛ termYears مشتقّ (وإلا تناقض الصفّ نفسه)
  terminatedOn DateTime?           // عيب ٣: بدل active — الفاعلية تُشتقّ: terminatedOn==null && now<=expiresOn
}
// Tender: fieldId String  (عيب ٤: NOT NULL بعد التعبئة — لا مناقصة بلا حقل؛ MCT يُفتح عند الإنشاء فيلزم FA)
// Operator: يُحذف financialAuthorityUSD (لا رقم مستوى-مشغّل حتى للتجزئة — يُحسب على القراءة)
```

### 1.2 استنباط الصلاحية + كشف التجزئة (٧.٢) — الموضعان معاً
- `faFor(tender)` = `tender.field.serviceContract.financialAuthorityUSD` — لا ثابت، **فشل مغلق** عند التعذّر (يُحذف `?? FINANCIAL_AUTHORITY_USD` المفتوح في `store.tsx:358` واختبار اليتيم `store.test.ts:357`؛ الخادم يفشل مغلقاً أصلاً `?? 0`).
- **التجزئة:** التجميع يبقى `(operatorId, budgetCode)` (منعاً للقفز بين الحقول للتهرّب)، والعتبة = **أدنى صلاحية عقد** بين حقول المجموعة. توقيع `detectSplitRisk(requests, fa)` يبقى؛ المستدعي يحسب min-FA.
- **موضعان يتغيّران معاً:** الخادم `tenders.service.ts:127` **و** المعالج `RequestWizard.tsx:44` — وإلا رأى المستخدم معاينة نظيفة ورفضها الخادم.

### 1.3 إنشاء المناقصة + المعالج
- `fieldId` **إلزامي** عند الإنشاء + بوابة `field.operatorId === user.operatorId` أو 403.
- المعالج: **منتقي الحقل يصير خطوة مبكّرة** قبل التقدير/المسار (الثلاثة تعتمد على FA المشتقّة من الحقل).

### 1.4 API
- `fields/` module: `GET`/`GET :id` (READ_ROLES) · `POST`/`PATCH` (SUPER_ADMIN).
- `service-contracts/`: `PATCH :id` لتعديل الصلاحية (مسوّغ ≥20، مُدقَّق) · التجديد PATCH مُدقَّق. `assertScopeConsistency` تمتدّ للحقول.
- **`capabilities.ts` (رِبل خامس):** نقاط الحقول/العقود تُضاف للسجل الـ43 + `CapDomain` + `COUNTED_DOMAINS` + `DOMAIN_ORDER` (UserProfile) + تسميات المجال بالترجمتين — وإلا كذبت شاشة الحوكمة.

### 1.5 شاشة المشغّلين (رِبل ثالث — تنتقل الصلاحية للعقد)
- `SET_OPERATOR_FA` **يُتقاعَد** ويحلّ محلّه `SET_CONTRACT_FA` بنفس دلالة الرفض (`fa-invalid` عند ≤0، no-op عند التساوي).
- `CREATE_OPERATOR` **يفقد وسيط `financialAuthorityUSD`** — الصلاحية تأتي عند إنشاء العقد.
- عمود الصلاحية في الشاشة يبقى **عرضاً مشتقّاً** (نطاق/قائمة صلاحيات عقود المشغّل).
- **خريطة تسميات التدقيق تُبقي `SET_OPERATOR_FA`** القديمة تُعرَض (صفوف تاريخية 8.1-e، لا تُحذف) + إعادة كتابة `ar.json` (`colFa`/`faHelp`/`faImpact`/`faReasonPh`).

### 1.6 الشاشات + الترحيل
- شاشة **الحقول** `#/admin/fields` + **ملف الحقل ٣٦٠°** (البيانات، مناقصاته، عقد الخدمة والصلاحية) — نظير `Vendors → EntityProfile`.
- **البذرة (ترحيل v6):** كل مشغّل له **حقل رئيسي** صلاحية عقده = صلاحيته اليوم (5M/3M/2M)، وكل مناقصاته القائمة تُسنَد إليه؛ بقية الحقول (إلى ١٣) عقود بصلاحيات واقعية بلا مناقصات. فيتطابق السلوك القديم تماماً (بما فيه تجميع التجزئة).
- **معيار القبول:** اختبار الترحيل يؤكّد `aboveOwnFA` متطابقة قبل/بعد لكل **الثلاث** (t1/t2/t3) · كل مناقصة لها `fieldId` · لا رقم مستوى-مشغّل مخزَّن.

### 1.7 تصحيحات دراسة الأثر (النواة + التعليمات — «النصّ الإنجليزي يعلو»)
تعدّل هذه ما أوصى به المستشار حيث خالف النصّ الحاكم:
- **§7.2 التجزئة (المطابقة: جزئي):** حكم المستشار «تجميع بالمشغّل + أدنى صلاحية» **غير مطابق** — النصّ يربط المنع بـ«الصلاحية المناسبة» = **صلاحية العقد/الحقل**. أدنى-صلاحية-عبر-الحقول يطبّق عتبة حقلٍ على مناقصة حقلٍ آخر (3M مشروعة في حقل صلاحيته 5M تُعلَّم زوراً مقابل 2M). **التصحيح:** التجميع على **الحقل/العقد** (مفتاح `fieldId`، أو إثبات أن `budgetCode` أحاديّ الحقل — §2.16 يربط الموازنة بالحقل)، والمقارنة بصلاحية ذلك الحقل نفسه. **و§7.2 «لغرض التهرّب حصراً» نيّة لا تحدّدها عتبة → يبقى تنبيهاً «ينبّه» لا رفضاً صلباً.**
- **§6.9 MCT (المطابقة: جزئي):** «عند الإنشاء فقط» **يُقصّر عن المُشغِّل** — بما أن الصلاحية صارت متغيّرة (`SET_CONTRACT_FA`)، مناقصة أُنشئت تحت الصلاحية قد تتجاوزها **وهي قبل-الإحالة**، فتبلغ الإحالة دون تفعيل MCT الذي يوجبه §6.9. **التصحيح:** يُعاد تقييم مسند «فوق الصلاحية» **حتى الإحالة** للمناقصات قبل-الإحالة عند تغيّر الصلاحية؛ **المُحالة لا تُمَسّ** (لا رجعية عليها).
- **§12.2 ROC (مطابق):** يبقى الحدّ الأدنى `max($2,000,000, 0.25×FA)` — الـ2M أرضية «أيّهما أعلى» لا مشتقّة.
- **نقاء المحرّك (النواة: يُجهِد قليلاً):** `serviceContractEffective()` و`contractTermYears()` وعتبة التجزئة **تُصدَّر من scpp-rules** لا تُضمَّن في المتجر/API/الشاشة (نظير `variationOrdersCap`/`banWithinLimit`).
- **fa=0 ليس فشلاً مغلقاً موحّداً (النواة):** للـMCT محافظ، لكن للتجزئة **متساهل** (`detectSplitRisk` يتخطّى ما ≥ الصلاحية، فـ0 لا يعلّم شيئاً). فحقل بلا عقد = **رفض إنشاء المناقصة**، لا تمرير `fa=0`.
- **`Tender.operatorId` يصير مشتقّاً** من `field.operatorId` (مخزَّن-مشتقّ جديد): يُحذف ويُشتقّ عبر الحقل، أو يُوثَّق ثابت `operatorId===field.operatorId` (يُفرَض الآن عند الإنشاء فقط).
- **البذرة:** مالك الحقل **الثالث عشر** يُحدَّد صراحةً (١٢ مشغّلاً، ١٣ حقلاً → مشغّل يملك حقلين)، وكل الـ١٣ لها عقود.

### 1.8 دَين مؤجَّل موثَّق (من مراجعة الدفعة د)
- **`/service-contracts` API غير مبنيّ:** `CREATE_FIELD`/`SET_CONTRACT_FA` محليّان (`CLIENT_ONLY`) — في وضع الـAPI لا مسار كتابة للخادم، فالصلاحية في Prisma مجمّدة على قيم الترحيل. **عولج مؤقتاً:** محرّر الصلاحية **مُعطَّل بلافتة في وضع الـAPI** فلا يوهم بتغيير لا يصل الخادم. **يبقى:** بناء `service-contracts PATCH` (مشرف رئيسي، مسوّغ ≥20، مُدقَّق) عند تفعيل وضع الـAPI فعلياً.
- **دورة حياة العقد الناقصة:** لا فعل يعدّل تواريخ العقد أو يُلحِق عقداً بحقل بلا عقد — تحسين لاحق (الرافض يمنع الحالة الميتة، لكن لا إصلاح لها).
- **حالة المسار ١: مختومة وخضراء** (٢٨٨ اختباراً) بعد جولتَي مراجعة عدائية (٦ عيوب كود + ٩ ملاحظات دفعة د، كلّها معالَجة أو موثَّقة).

## المسار ٢ — إحياء الكود الميت + التقويم الديناميكي (مُعاد التصميم بعد الهجوم)

**تصحيح جوهري (المستشار):** الفرضية الأصلية «حقل بيانات واحد مفقود» **خاطئة**. الناقص بنيةُ بيانات: (أ) مصدر عطل — `IRAQ_CALENDAR.holidays = []` فارغ ثابت والمتجر لا يحمله، (ب) مسار إدخال عطاء — `ADD_BIDDER` يتيم لا تُطلقه شاشة، (ج) دلالة وقت. إحياء القواعد دون ذلك يحوّل بوابةً غائبة إلى بوابة **تُظهر الأخضر ولا تعمل** — وهو في منصّة امتثال أسوأ من الكود الميت (أثر تدقيق يشهد بإنفاذ لم يقع). لذا يُدمَج التقويم الديناميكي هنا (كان في المسار ٤).

### 2.1 التقويم الديناميكي في المتجر (نُقل من المسار ٤)
- `store.tsx`: `holidays: string[]` في الحالة، ودالة `calendarOf(state)` تبني `WorkingCalendar` حيّاً من العطل بدل `IRAQ_CALENDAR` الفارغ.
- كل استدعاء قاعدة يمرّر التقويم الحيّ: `effectiveClosingDate`/`mct`/`roc` تأخذ `calendarOf(state)` لا الافتراضي الثابت.

### 2.2 حقل تاريخ غلق العطاء — بدلالة وقت صريحة
- `Announcement.closingAt DateTime` · `Bidder.submittedAt DateTime?`.
- **دلالة الوقت (تصحيح):** `effectiveClosingDate` يعيد ISO بلا وقت؛ التمديد للعطلة يجب أن **يحمل وقت اليوم الأصلي** وإلا صار عطاءٌ 00:01 من يوم التمديد «متأخراً». يُثبَّت في الاختبار.
- **الترحيل يملأ `closingAt`** للمناقصات المعلنة القائمة (من `plannedTo` لمرحلة الإعلان) — لا للبذرة وحدها.

### 2.3 توصيل القواعد — بفشل مغلق
- `effectiveClosingDate` (11.3.4-e) عبر التقويم الحيّ.
- `isLateBid` (10.6.1) — يرفض `submittedAt > closingAt`. **فشل مغلق:** مناقصة معلنة بلا `closingAt` تُرفَض لا تُقبَل (`Date.parse(undefined)=NaN` كان يفتح البوابة صامتاً).
- `singleBidAcceptable` (15.3) — عطاء وحيد يتطلّب ≥21 يوماً، يُفحَص عند الإحالة.
- **تنسيق مع الخطة الأخرى:** إدخال العطاء (`addBidder`) تملكه م٤ في `UI-METHODOLOGY-PLAN.md` — يُحسَم أيّ خطة تبنيه أولاً قبل البدء تفادياً لإعادة العمل.
- **معيار القبول (مُصحَّح، لا يُخدَع بـgrep):** عطاء بعد الغلق يُرفض **عبر شاشة فعلية** · مناقصة معلنة بلا `closingAt` تفشل مغلقةً · عطاء وحيد بمدّة <21 يوماً يُوقَف · إضافة عطلة **حقيقية** (لا عطلة أسبوع) تمدّد غلقاً مفتوحاً في التطبيق المُشحَّن، لا بحقن تقويم مخصّص في الاختبار.

### ✅ 2.تنفيذ — ما بُني فعلاً (الدفعتان هـ + و · 309 اختبار · typecheck + build نظيفان)

**الدفعة هـ — التقويم الديناميكي:** `State.holidays: string[]` + `calendarOf(state)` + إجراءا `ADD_HOLIDAY`/`REMOVE_HOLIDAY` (مدقَّقان، محليّان حتى تصل شاشة العطل م٤). مُرِّر التقويم الحيّ إلى **كل** موقع أيام‑عمل في الويب (بارامتر `cal` مطلوب في دوال الاشتقاق يفرضه المُصرِّف: `tenderStatus`/`stageDevWd`/`tenderDeviationWd`/`deriveTasks` + `mctCycleStatus`/`workingDaysBetween` في المكوّنات + `addWorkingDays` في المعالجات). اختبار ديناميكية يُثبِت أن عطلة وسط النافذة تنقل الحالة من `progress`→`risk` وتُنقص العدّاد يوماً — دون حقن تقويم مخصّص.

**الدفعة و — إحياء الكود الميت:** `effectiveClosingDate`/`isLateBid`/`singleBidAcceptable` صارت لها مستدعون حقيقيون في المتجر والـAPI والواجهة (`FileBidders` يعرض الغلق المُشتَقّ + تحذير §15.3؛ `BidderAddDialog` يعرض حقل تاريخ تقديم اختيارياً مع بوابة تأخّر).

**انحرافات مقصودة عن نصّ الخطة (لعرضها على المستشار):**
1. **`closingAt` مُشتَقّة لا مُخزَّنة** — نصّ §2.2 قال `Announcement.closingAt DateTime`؛ لكن الحوكمة C2 «المشتقات تُحسب ولا تُخزَّن» تحكم: الغلق = `effectiveClosingDate(publishedOn + periodDays, cal)` + نهاية اليوم. النتيجة: **لا تغيير مخطط للإعلان ولا ترحيل** للغلق. المُخزَّن الوحيد هو `Bidder.submittedAt` (datum حقيقي غير مُشتَقّ). دلالة الوقت مضمونة بثابت `T23:59:59Z` (نهاية يوم الغلق) فالتمديد يحمله بلا تغيير.
2. **بوابة التأخّر لا تُطلَق بساعة الحائط** — `ADD_BIDDER` يفحص التأخّر **فقط** حين يُسجَّل `submittedAt` صراحةً؛ إغفاله = المسار السريع القائم بلا كسر (تشهد له اختبارات bidderAdd). حين يُسجَّل: يُرفض إن تجاوز الغلق، و**يفشل مغلقاً** إن لا غلق (إعلان غير منشور). هذا يتفادى رفض عطاءات البذرة/الطرق المحدودة (م٦ بلا مرحلة إعلان) زوراً.
3. **قراءة عطل api-mode مؤجَّلة للمسار ٤** — `GET /api/holidays` موجود لكن الويب يقرؤه مع شاشة العطل؛ حتى ذلك الحين تقويم الويب في api-mode فارغ (الخادم يحسم تقويمه بنفسه لكل قاعدة، فالحوكمة سليمة).
4. **لا رفع مفتاح التخزين** — `holidays` إضافيّ بقيمة افتراضية آمنة، فبلوب v8 بلا عطل يُحمَّل ويُملأ `[]` (اختبار ترحيل يثبته) بدل رفع المفتاح وتيتيم البلوب.

### 🔁 2.معالجة مراجعة المستشار العدائية (فيبل 5) — كل النقاط الأربع الأولى أُغلقت (313 اختبار)

### 3.0 خمسة أفخاخ «الأخضر الذي لا يعمل» (حكم المستشار — تُقرأ قبل أول سطر كود)
1. **فخّ المعيار قبل الكود:** المخالفة **ليست** «دون 20%» — النسبة «مقترحة» في وثائق المناقصة باستثناء موثَّق. المخالفة = **غياب النصّ من الوثائق ∧ غياب سجل استجابة/مبرّر** (C8.1 ∧ C8.2 معاً). صُحِّح في §3.3 — يُحترَم في المحرّك حرفياً.
2. **فخّ انقلاب بوابة المنشأ:** C8.6 يحكم المواد الحرجة **المستوردة**. أول سؤال في البوابة «مستورد؟» — بوابةٌ ساذجة «حرج + منشأ ∉ الأربعة → رفض» **ترفض المصنوع عراقياً** فتقلب غرض §9. نمذج `imported`/`origin`/`oemAuthorized` حقولاً متمايزة، ومسار قائمة مجهّزي الوزارة بديلٌ نصّي.
3. **فخّ الولاية (بند←مرحلة) — تُكتب خريطة قبل النمذجة:** C8.1 نصّ الوثائق → الإعلان/الموافقة · C8.2 سجل الأدلة → مستوى المناقصة قبل الطرح · C8.6 المنشأ → **رفض عند التقييم الفني** (10.6.18) · C8.8 فحص الجهة + شهادة منشأ مصدّقة → **قائمة تحقق ما بعد التعاقد** (10.6.17/10.6.19، «بعد التعاقد» نصاً). جعلُها كلَّها بوابات إحالة أو كلَّها تحذيرات = مسرح امتثال.
4. **فخّ النطاق والصلاحية:** الشرط فوق الصلاحية في الحفر/الهندسة-**الإنشاء**/المواد الثقيلة — سمِّ `ENGINEERING_CONSTRUCTION` أو وثّق الضمّ وإلا هربت EPC. والصلاحية مشتقة قابلة للـnull → المرجع `aboveOwnFA` **المغلق فشلُه** لا مقارنة يدوية جديدة.

### ✅ 3.التصميم المُصادَق (خريطة بند←مرحلة + ٥ تعديلات المستشار — يُبنى على هذا)

**الخريطة (بند · مرحلة · حكم):** C8.1 صياغة الوثائق → **بوابة نشر** · C8.2 مشاركة/عذر → **تحذير مشتق** · C8.3 مصدر وحيد → سماح · C8.4 أهلية → بوابة 10.4 + **سجل حكم 25.2** · C8.5 قائمة 17 → مرجع · C8.6 المنشأ → **بوابة تقييم فني (للمستورد وحده)** · C8.7 قائمة الوزارة → مسار بديل يُشبع C8.6 · C8.8 فحص+شهادة → **وثائق مرحلة مطلوبة** بعد التعاقد.

**التعديلات الخمسة (حاكمة):**
1. **فصل الحكم المركّب — الخطأ الجوهري:** C8.1 واجبُ **صياغةٍ على المقاول** («تنص الوثائق») وC8.2 عذرُ **مشاركةٍ للمتناقص**؛ دليلُ C8.2 لا يعذر وثيقةً أغفلت النصّ. فحصان منفصلان: **(C8.1)** يسري ∧ لا نصّ في الوثائق → **مخالفة صياغة تحجب النشر** (بند شرطي في `checkAnnouncement` كشروط 11.1، تلزم النشرَ المقبل فقط). **(C8.2)** يسري ∧ لا مشاركة ∧ لا سجل استجابة/دليل → `violating`؛ `exempt` = دليل مسجَّل (فاعل+تاريخ+وثيقة، سجل بدرجة تدقيق).

## المسار ٤ — شاشة إدارة العطل (التالي بعد م٢ · يُقفل آخر شرط معلّق من م٢)

### ✅ 4.تنفيذ — ما بُني (الدفعتان ز + ح · 316 اختبار · typecheck + build + متصفّح نظيف)

**الدفعة ز — العمود الفقري (فصل الدورَين + توصيل الخادم):** فُصل قرار «محلي في api-mode» عن `NON_AUDITED`: صار `if (CLIENT_ONLY.has)` وحده (لا `NON_AUDITED || CLIENT_ONLY`)، وأُضيف `RESET`/`HYDRATE`/`UPSERT_TENDER` إلى `CLIENT_ONLY`، وأُخرج العطلان منها. `runAction` يوصّل `POST /holidays` (يعيد `reload`) و`DELETE /holidays/:date?reason=`. خادم `HolidayDto` اكتسب `reason` اختيارياً في سطر التدقيق. **هذا سدّد آليّة دين م٥ رقم ٢ جزئياً** (يبقى تطبيق التدقيق الذاتي لرفض RATIFY/ADD_BIDDER لِم٥). اختبارا الإرسال أخضران (RESET محلي · RATIFY للخادم).

### 🔁 4.معالجة مراجعة المستشار الثالثة (م٤) — أُغلقت الأربعة (318 اختبار)
- **[حاجز] `default` الفاشل في `runAction`:** بعد فصل الدورَين صار فعلٌ منسيّ من القائمتين يسلك المسار الخادمي ويعود `ok:true` بلا عمل (قناة الصدق تكذب). العلاج: `default: throw new Error('no-route:'+type)` → يمرّ عبر catch الإرسال فيصير `ok:false`. تحقّقتُ: الأفعال الخادمية الـ25 كلّها لها فروع، فلا فعل حاليّ يسقط.
- **[متوسط] `reason` إلزامي على الخادم:** `HolidayDto.reason` صار `@Length(20,2000)` مطلوباً، والحذف يرفض `reason<20` (`BadRequestException`) — حارس الكتابة لم يعد أضعف من حارس العرض («الخادم يعيد إجراء الفحوص»).
- **[أمانة واجهة] `holidays` صارت `{date, name?}[]`:** الاسم المجموع يُعرَض الآن (عمود Name)، `calendarOf` يشتق التواريخ، `holidaysImpact` يعمل على التواريخ، والتحميل يُطبّع الشكل القديم `string[]` عبر `normHolidays` (اختبار ترحيل يثبته). تحقّق متصفّح: صفّ يعرض «ذكرى تأسيس الشركة».
- **[اتساق] معجم التدقيق موحَّد:** الخادم صار يكتب `ADD_HOLIDAY`/`REMOVE_HOLIDAY` (كأسماء أفعال العميل، لا `HOLIDAY_ADD`).
- **[غير حاجز] سطر عام في التنبيه:** «كل عدّادات أيام العمل (الانحرافات، مهل 6.9) تُعاد قراءتها». عدُّ قضايا MCT الدقيق مؤجَّل لم٥.
